### Form builder does not follow the application phase until you change tabs

-> Topic 1

Opening, closing and reopening applications changes whether you can add a field in the form builder.

### Market tab hover makes the label invisible

-> Topic 1

### Market header stays pinned while the content below scrolls

-> Topic 1

On the market setup page, the header should stay aligned to the top and always visible.
The header is the market title, the navigation tabs, and the market status with the Close applications and More buttons.
Only the section below it should scroll.
Today the whole page scrolls, and scrolling hides this important information.

> Note for extraction: `docs/design-system.md` and AGENTS.md say "the PAGE scrolls" and warn against a viewport-height shell with nested scrollers.

### Applications tab is vertically centered instead of top-aligned

-> Topic 1

When the window is not very tall, the Applications tab content is centered vertically instead of aligned to the top.
It should be aligned to the top.
It should also stretch to fill the available height, like the other tabs.

### Spike: use Jev to draft an application form from an uploaded CSV

-> Topic 4

An organizer uploads a CSV of past vendors and gets back a draft application form in our format, ready to edit in the form builder.
Research whether Jev can do this, and how to run it locally on CPU.

**What Jev is** (researched 2026-09-26, released 2026-09-19, so everything below is days old and should be re-checked).
Jev is TypeSafe AI's "System One" model.
It does not generate text.
It takes a text state plus typed questions and returns one of three typed answers, each with calibrated probabilities:

- **Choice**: pick one of up to 255 labelled options.
- **Score**: place the input on an ordered 2-10 level scale.
- **Noul**: probability that a yes/no statement holds.

Text in only, 32K context, answers in roughly 70-500 ms, about $0.042 per million input tokens with free output.
SDKs: `pip install typesafe-sdk` (Python 3.10+) and `@typesafe-ai/sdk`.

**Running it locally on CPU: official Jev cannot.**
It is closed-weight and hosted-only, with no on-prem build and no announced plan for one.
The local route is an independent "Jev-like" open model that uses the same three primitives:

- **Laya** (421M params, Apache 2.0, `pip install laya`): under 1 GB, about 1 second per question on a plain CPU. Its author claims it beats Jev on a typed-decision benchmark; nobody has checked that independently.
- **JEV-CPU** (Meanblock on Hugging Face, MIT): a CPU adaptation of SemIf on Qwen3-0.6B, about 3 GB RAM, no GPU. Explicitly not affiliated with TypeSafe.
- The larger alternatives (decider-4b, Winnow-12B, OpenJev) need a GPU, so they are out for a CPU-only deployment.

None of these is TypeSafe's model, and their accuracy is their authors' claim, not TypeSafe's.
Several of the pages I found read like SEO content, so the spike should confirm each claim against the model's own repo.

**Where it fits our form format** (`FormField` in `back-end/datatypes.py`).
Jev can classify, but it cannot write text, so it could only fill in part of a form:

- Deterministic, no model needed: `label` from the column header, `key` slugified from the label, `options` from the column's distinct values, `order` from column order.
- Jev-shaped questions, one set per column, with the header plus a sample of values as state:
  - Choice: `type` from the eight types (`text`, `number`, `select`, `multi_select`, `checkbox`, `date`, `email`, `file`).
  - Choice: whether this column answers an essential question (dates, max dates, tier, section, table type) or is a custom field. This matters most, because an essential column must not become a duplicate custom field.
  - Noul: `required`.
  - Noul: "this column is applicant data, not an organizer's note" (for example "paid?" or "notes"), so columns that are not questions can be dropped.
- Jev cannot write `help_text` or a cleaner label; those would need a generative model or stay blank.

**Questions for the spike to answer.**

- Is a rule-based heuristic (regex on values, header keyword matching) already good enough? That baseline should be measured before adding a model.
- Accuracy of Laya / JEV-CPU against hosted Jev on real organizer CSVs.
- Latency: about 1 s per question on CPU, times roughly 4 questions per column, times 20-40 columns, adds up to minutes. Can questions be batched, or does the run need to be a background job?
- Privacy: the CSV holds vendor PII. Send only headers plus a few sample values, and prefer local inference so none of it leaves our infrastructure.
- Deployment: can a 0.4-0.6B model live beside the Flask back end in our containers, and at what image size and memory cost?
- Relationship to the existing CSV import, which maps a CSV onto a form that already exists; this idea runs the other way.
